Fuzzy Identity-Based Data Integrity Auditing for Reliable Cloud Storage Systems

What this application does

It demonstrates the four-role workflow: KGC approves users and issues ordinary identity-associated application keys; users pass synthetic attribute checks and encrypt files; TPA issues challenges; the local cloud simulator reads current ciphertext; TPA checks returned bytes against trusted upload-time SHA-256 block metadata.

What remains outside this prototype

The research paper uses Setup, Extract, MetadataGen, Challenge, Response and Verify algorithms involving bilinear pairings, threshold sharing, fuzzy identity-based signatures and homomorphic authenticators. This application does not reproduce their mathematics, soundness proof, fuzzy extractor, erasure coding, biometric acquisition or constant-size publicly verifiable proofs.

Signature images are previews, not biometric recognition. Application keys are not identity-based cryptographic private keys. There is no claim of production security or proof of retrievability.

Trusted metadata is O(number of blocks). Full audits transfer all encrypted bytes internally. A sampled PASS covers selected blocks only. Nonces reject protocol mismatches/replays but cannot prevent a malicious cloud from retaining old correct data.

Roles share one Java process and one computer. The master key is in trusted local storage; database file keys are wrapped. Operating-system administrators can access both trust domains. The manifest checksum diagnoses accidental changes and is not an adversarial signature.

AI security, mobile clients, multi-cloud support and faster biometric authentication remain future work from presentation slide 14.
